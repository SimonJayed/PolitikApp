# Legislative migration readiness and 20th Congress pilot

**Decision pending.** Shared Supabase is on PostgreSQL 17.6. Flyway reports V28 as the latest successful migration and V29 and V30 as the only pending migrations with all locations enabled. Both feature tables are absent. The recommended sequence is to harden and apply V29 first, validate it, then apply V30 and validate it before a separately authorized pilot load. Shared inspection used read-only database connections. The pilot is a local proposal.

## Backup, execution, validation and rollback

1. **Before any write**, record the exact approved artifact and SHA-256 of its migration files. Recheck Flyway, table absence and the preservation baseline. Record the provider backup or PITR restore point. Make an encrypted, access-restricted custom-format database dump, including the complete application schema, data and `public.flyway_schema_history`. Capture effective grants, owner and role memberships separately. Verify the dump with `pg_restore --list`, calculate its checksum, and restore it into a private PostgreSQL 17 instance. The read-only inspection snapshot is a baseline record and does not replace the backup.
2. **Rehearse both changes on the private restore.** Before V29’s first shared application, include the targeted privilege revocation in its separately approved release SQL, following the guarded role approach in V30. Recompute the checksum after that change. Test `PUBLIC`, `anon`, `authenticated`, `service_role` and the real backend role, including inherited and owner privileges. Measure the restore and reversal. Rehearse application administrator access, citizen denial, stale and unpublished citation behavior and the public projection without private notes.
3. **V29 after separate approval.** Pause deploy-time migrators and scheduled writers. Run one controlled Spring Flyway invocation with the `supabase,citation-reviews` profiles, target `29`, citation reviews disabled, Hibernate schema validation, and scheduled news and Congress imports disabled. Confirm a single successful V29 history row with the reviewed checksum, an empty review table, RLS, expected role access and unchanged baseline. Keep the installed migration location available to each app instance that runs Flyway validation.
4. **V30 after approval and V29 verification.** Use one controlled invocation with the `supabase,citation-reviews,legislative-accountability` profiles in that order and target `30`. Keep the legislative feature disabled during schema and permission checks. Confirm the V30 history entry, UUID foreign key, checks, duplicate constraint, index, empty table, role access and unchanged baseline. Recheck that public routes return the correct empty state and authenticated contributors cannot manage drafts. Keep all three installed migration locations in later configurations.
5. **Pilot as a separate transaction after approval.** Back up affected tables and verify the frozen candidate manifest against current politician/chamber memberships and existing record keys. Use the application’s validation and an administrator-authorized batch or equivalent transaction on the private restore first. Import as pending review, return a per-row disposition, and publish only when an authorized reviewer confirms the source. Confirm that draft records remain private and that ranked scores, baseline digests, 970 profiles, 53 published timeline records, six withdrawals and 44 published submissions are identical to the preflight.
6. **Rollback starts with feature flags.** Disable the affected feature and retain its migration location while the schema remains installed. For pilot rollback, use the recorded batch IDs to withdraw only the approved pilot rows or revert the still-open transaction. Preserve review history. If physical reversal is separately approved, stop writers and export the feature tables and precise history rows. Rehearse on the private restore. Remove only the approved latest table and its matching history entry in one guarded transaction. Reverse V30 before V29 if both need removal. Use no cascade and stop if the version, checksum or dependencies differ. Re-run Flyway validation and the preservation baseline before restarting.

## Proposed semi-automated import

1. Build a document manifest from numbered journals and source directories. Store chamber, Congress, regular or special session, journal number, sitting date, official URI, final URL, hash and original pagination. Save fetch outcomes and corrections separately. Prefer documented structured interfaces for identity and discovery. Use HTML for official rosters and PDFBox for named journal lists. Retain coordinates for multi-column pages and review low-confidence OCR or inaccessible documents through the official archive.
2. Extract attendance only from the dated named roll or appendix. Keep excused status and other documented official activity distinct where the journal supports the mapping. Extract votes only from named blocks and attach their chamber, current sitting date, measure ID, vote stage and group. Apply explicitly published corrections first. A chamber tally or voice vote cannot supply each person’s decision. Committee rosters should retain the exact role and source date, with appointment and end dates left empty unless supported.
3. Resolve a candidate by existing politician ID, official name or identifier and the linked chamber membership for Congress 20. Review surname collisions, initials, party-list replacements and membership periods manually. Stage a deterministic key for politician, chamber, term, kind and journal/date or measure/vote or committee/role/start date. Detect existing and repeated keys before writes. Save a source-level revision separately so a corrected file can be reviewed without duplicating the event.
4. Generate a review file with all three types, separate extraction and verification statuses, and an audit disposition per row. Run a no-write preview. Route ambiguous identity, OCR rows, changes to vote blocks and evidence gaps to an administrator. Permit publication through the existing V30 workflow only after approval. Use retries with rate limits and honor source access restrictions. Leave Open Congress source-reported labels intact.

## Pilot

The [machine-readable pilot](data/legislative-accountability-pilot-20th-congress-2026-11-27.json) contains **18 proposed rows for six existing politicians**. Each person has a source-backed attendance row, a named vote and a committee assignment. Every input includes an official citation and a verification note. Each identity is bound to a shared politician UUID and the imported 20th Congress membership. The pilot stages all rows as Pending Verification, with six House journal rows explicitly marked as blocked by the current allowed-host rule.

The local validation matched all 18 rows to the expected live politician IDs, source person IDs and chamber memberships, with 18 unique record keys. The current V30 application validator accepted 12 rows and rejected exactly the six House journal citations marked as blocked. In isolated PostgreSQL, the 12 eligible drafts inserted in one transaction. Repeating the batch produced zero additional rows. Zero rows were eligible for public display, and rollback left zero pilot rows. The input check measures application compatibility separately from URL availability.
